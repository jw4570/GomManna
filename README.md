# 곰만나 · GomManna

**우리 곧, 만나요.**

곰만나는 모임 방에서 일행의 위치와 상세 위치 메모를 공유해 다시 만나기 위한 연락과 대기를 줄이는 iOS 앱입니다.
6자리 초대 코드 또는 QR로 방에 참여하며, 각자 위치 공유를 켜거나 끌 수 있습니다.

## 주요 기능

- **모임 만들기·참여:** 초대 코드 또는 QR로 방에 참여합니다.
- **위치 공유 ON/OFF:** 켜면 같은 방 참가자에게 최신 위치가 보입니다. 끄면 위치·메모·사진이 함께 숨겨집니다.
- **상세 위치:** 메모에 작성 시각과 당시 위치를 함께 남기고 사진을 첨부합니다.
- **모임 종료:** 방장이 직접 방을 종료합니다.

아래 개발 현황은 서버·앱의 연결 상태를 구분합니다. 지도 마킹과 동물 프로필 선택은 기기 내 기능이며, 현재 서버에는 대화·공유 마킹·프로필 동기화 API가 없습니다.

## 개발 현황

| 영역 | 현재 상태 |
|---|---|
| iOS | 인트로·홈·방 생성/참여·지도·설정·초대·프로필·메모/사진 화면과 ViewModel 구현 |
| 앱 데이터 | 기본 실제 API 연결. 환경 변수로 Mock 전환, 익명 인증·참가 상태 복원 지원 |
| QR | 서버 초대 코드·QR payload를 사용하며 앱 카메라 인식·딥링크 참여 지원 |
| 위치 | GPS 콜백 전송·백그라운드 공유·공유 중단 구현. 잠금 상태 지속 동작은 실기기 검증 필요 |
| 서버 | 익명 세션·방·위치·공유 상태·메모 API 및 사진 저장 연동 구현 |
| DB | 서버 전용 Supabase PostgreSQL 스키마와 private Storage를 사용 |
| 검증 | C/C++·DB 통합 테스트와 iOS Mock 흐름·취소·백그라운드 위치·사진 식별 검증 |
| 배포 | HTTPS 서버 연결. 실기기 검증과 정책 확정·전체 사용자 삭제 API는 출시 전 필요 |

## 기술 구성

| 영역 | 기술 |
|---|---|
| iOS | Swift, SwiftUI, Observation, MapKit, Core Image |
| 서버 | C++20, C, CMake, cpp-httplib, nlohmann/json, OpenSSL |
| DB | Supabase PostgreSQL, libpq |
| 인증 | C++ 서버에서 발급하는 익명 토큰과 SHA-256 해시 |
| 테스트 | CTest, Python 기반 HTTP·PostgreSQL 통합 테스트 |

데이터 연결 구조는 `iOS 앱 → C++ HTTP API 서버 → Supabase PostgreSQL`입니다.
DB 접근과 권한 확인은 C++ 서버에서 처리합니다. Supabase RPC와 Supabase Auth는 사용하지 않습니다.

## 실행 방법

### iOS

1. `GomManna.xcodeproj`를 Xcode로 엽니다.
2. `GomManna` Scheme과 실행할 시뮬레이터 또는 기기를 선택합니다.
3. 빌드하고 실행합니다. 기본은 실제 서버를 사용하며, 서버 없이 확인하려면 아래 Mock 전환 설정을 사용합니다.

앱 타깃의 Deployment Target은 `$(RECOMMENDED_IPHONEOS_DEPLOYMENT_TARGET)`이며 현재 Xcode에서 **iOS 17.0**으로 해석됩니다. 해당 SDK와 실행 환경이 필요합니다.
실기기 실행 시에는 자신의 개발 팀과 서명 설정을 사용합니다.

### 앱의 API 연동

기본 실행은 `https://32.236.33.77`의 실제 API를 사용합니다. 주소는
`App/Configuration/AppEnvironment.swift`에서 설정하며 Xcode Run 환경 변수
`GOMMANNA_API_BASE_URL`로 덮어쓸 수 있습니다. HTTP 인증서는 우회하지 않습니다.

- 최초 실행에 익명 사용자를 발급하고 토큰을 Keychain에 저장합니다. `GOMMANNA_ACCESS_TOKEN` 수동 설정은 필요 없습니다.
- 방 생성·참여는 서버 응답의 ID를 사용합니다. 현재 방 ID와 내 사용자 ID만 기기에 저장하고, 재실행 시 서버에서 참가 상태를 다시 확인합니다.
- 초대 화면은 서버 초대 코드·QR payload를 사용합니다. `gommanna://join?code=ABCD23` 링크와 QR 카메라 스캔을 지원합니다.
- 모임 화면이 활성화된 동안 5초 간격으로 멤버를 조회합니다. 요청이 실패하면 10초 기다렸다가 재시도합니다. 백그라운드나 모임 화면 이탈 시 멤버 조회 반복 작업만 중단하고, 켜 둔 내 위치 공유는 계속합니다.
- 위치 공유 ON일 때만 세션이 소유하는 위치 서비스가 GPS 콜백을 받아 전송합니다. 백그라운드 Location updates와 위치 사용 표시를 설정하여 화면 잠금·다른 앱 사용 중에도 이어갑니다. 이동 거리 필터 없이 새 위치 콜백을 받되 전송은 최소 5초 간격으로 제한하며 고정 주기를 보장하지 않습니다. 공유 OFF·탈퇴·종료·권한 해제 때 중단하며, 강제 종료 후 자동 재개를 보장하지 않습니다. 다른 멤버가 모임을 종료한 경우 다음 조회/위치 전송 응답에서 이를 확인하여 중단합니다. 공유 epoch는 서버 응답을 사용하며 같은 epoch의 sequence를 증가시킵니다. 신선한 좌표에 대해서만 C 함수로 멤버 사이 거리를 표시합니다.
- 메모·사진 화면은 현재 위치를 전송한 후 메모를 저장하고 사진을 첨부합니다. 사진은 방향을 보정하고 축소한 JPEG로 업로드합니다. 상대 사진도 인증된 API로 조회합니다.
- 탈퇴·종료는 서버 요청이 성공해야 현재 방을 제거합니다. 서버가 종료·권한 상실을 알리면 참가 상태를 정리합니다.
- 토큰 만료를 임의로 새 사용자 발급으로 처리하지 않습니다. 안내를 확인하고 새 익명 사용자 생성을 선택해야 합니다. 기존 사용자의 복구 API는 없습니다.
- 현재 API에 대화·공유 마킹·프로필 동기화는 없습니다. 지도 상단 메모 버튼은 서버 메모·사진을 열고, 마킹과 동물 프로필 선택은 기기 내 기능으로 유지합니다.

### 홈 설정과 출시 문서

홈 상단 설정에서 프로필·화면 모드·위치/카메라 권한 상태·개인정보/모임 관리·정책 문서·문의·앱 버전을 확인할 수 있습니다.
운영자와 문의 주소는 `App/Configuration/LegalConfiguration.swift`에서 관리합니다.
정책 원문은 `Resources/Legal/`에 포함되어 오프라인으로도 열립니다.

현재 운영자와 이메일은 확정했지만 보유/파기 기간·저장 국가와 위탁/국외이전·시행일·공개 정책 URL은 미정이므로 초안으로 표시합니다.
전체 익명 사용자 삭제 API가 없어 데이터 관리의 공유 중단/메모 삭제/모임 탈퇴를 전체 삭제로 표시하지 않습니다.
[출시 전 남은 작업과 App Store 개인정보 표시 검토](docs/release/IOS_RELEASE_READINESS.md)를 확인하세요.

### Mock 데이터 전환

Xcode **Edit Scheme → Run → Arguments → Environment Variables**에
`GOMMANNA_DATA_SOURCE=mock`을 추가하면 같은 화면·ViewModel·Repository가 메모리 Mock을 사용합니다.
실제 네트워크와 Keychain에는 접근하지 않습니다. Xcode Preview도 자동으로 Mock을 사용합니다.

Mock 샘플 모임의 초대 코드는 `ABCD23`입니다. `Services/Mock/MockRoomData.swift`에서
샘플 멤버의 이름·좌표·공유 상태를 수정할 수 있습니다. Mock 상태는 앱 재실행 시 초기화됩니다.
사진은 입력 바이트를 보관하며 서버의 재인코딩·메타데이터 제거와 호출 빈도 제한은 재현하지 않습니다.

### iOS 연동 검증

```bash
tests/ios/run-flow-checks.sh        # 네트워크 없이 ViewModel/Repository 전체 흐름 검증
tests/ios/run-flow-checks.sh --live # 배포 서버에 테스트용 사용자·방을 생성해 검증하고 방 종료
```

Live 검증은 익명 사용자와 종료된 시험 방 기록을 남길 수 있습니다.
GPS 정확도, 카메라 스캔과 사진 선택 UI는 실기기에서 별도로 확인해야 합니다.

## 협업 흐름·브랜치 규칙

1. 작업 전에 이슈를 작성하고 담당자를 지정합니다.
2. 최신 `dev`에서 각자의 작업 브랜치를 만듭니다.
3. 하나의 작업 목적에 맞게 커밋합니다.
4. 작업 검증 후 **작업 브랜치 → `dev`** PR을 생성합니다.
5. 리뷰를 반영하고 팀원 1명 이상의 승인을 받은 뒤 `dev`에 병합합니다.
6. `dev`에서 앱·서버·DB의 통합 동작을 검증합니다.
7. 배포할 준비가 되면 **`dev` → `main`** 배포 PR을 생성하고, 승인 후 병합하여 배포합니다.

| 브랜치 | 용도 |
|---|---|
| `main` | 배포 기준 브랜치. 통합 검증을 마친 코드만 반영 |
| `dev` | 각 작업을 합치고 통합 검증하는 브랜치 |
| 작업 브랜치 | 개인별 기능·버그·문서 작업. `dev`에서 분기 |

```text
개인 작업 브랜치 → dev → 통합 검증 → main → 배포
```

`main`과 `dev`에는 직접 push하지 않고 PR로 반영합니다.
진행 중인 작업은 Draft PR로 공유할 수 있습니다. `dev`와 `main`은 계속 유지합니다.
위 규칙은 팀의 작업 기준이며, GitHub의 브랜치 보호·승인 강제 설정은 별도로 적용해야 합니다.

브랜치 이름은 `<type>/<이슈번호>-<작업명>` 형식으로 작성합니다.
작업명은 영문 소문자와 하이픈을 사용합니다.

```text
feat/12-room-create-api
fix/23-member-panel-drag
docs/31-api-guide
```

`type`은 아래 커밋 규칙과 동일하게 사용합니다. 서로 다른 작업을 한 브랜치에 섞지 않습니다.

## 커밋 규칙

[Conventional Commits](https://www.conventionalcommits.org/ko/v1.0.0/) 형식을 기준으로 사용합니다.

```text
<type>(<scope>): <변경 내용>

[필요한 경우 변경 이유와 영향]

Refs #이슈번호
```

| Type | 사용 목적 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `docs` | 문서 작성·수정 |
| `style` | 공백·정렬·포맷 변경, UI 디자인 변경은 해당하지 않음 |
| `test` | 테스트 추가·수정 |
| `build` | 빌드 설정·의존성·패키지 변경 |
| `ci` | CI/CD 워크플로 변경 |
| `chore` | 위 항목에 속하지 않는 저장소 관리 작업 |

- `scope`는 `ios`, `server`, `db` 또는 `room`, `map`, `chat`, `profile`, `auth`처럼 영향 범위로 작성합니다. 필요하지 않으면 생략합니다.
- 제목은 한글 또는 영어로 구체적으로 작성합니다. `수정`, `작업`, `완료`만 쓰지 않습니다.
- 한 커밋에는 하나의 논리적인 변경을 담습니다. 기능 수정과 무관한 전체 파일 정렬을 섞지 않습니다.
- 기존 API·DB·앱과 호환되지 않는 변경은 `!`와 본문의 `BREAKING CHANGE:`로 표시합니다.

```text
feat(room): 모임 생성 API 추가
fix(ios): 멤버 패널 드래그 떨림 수정
docs: 프로젝트 실행 방법 정리
build(server): PostgreSQL 연결 라이브러리 추가
```

이슈 연결이 필요한 커밋 본문 예시:

```text
feat(room): 모임 생성 API 추가

모임 생성과 방장 참여 등록을 하나의 트랜잭션으로 처리한다.

Refs #12
```

## 이슈 규칙

- **하나의 기능·버그·작업 단위로 이슈 하나**를 작성합니다. 범위가 크면 하위 작업으로 나눕니다.
- 제목은 `[유형][영역] 작업 내용` 형식을 사용합니다.
- 담당자를 지정하고, 관련 이슈·문서가 있으면 연결합니다.
- 라벨은 `feat`, `fix`, `docs` 등 작업 유형과 `ios`, `server`, `db` 등 영역을 기준으로 사용합니다.
- 버그는 재현 순서와 예상/실제 결과를 적습니다. 앱 버그는 기기·OS도 포함합니다.
- 동작에 필요한 API 입력·응답 형식이나 DB 변경은 구현 전에 이슈에서 합의합니다.

제목 예시:

```text
[Feat][Server] 모임 생성 API 구현
[Fix][iOS] 멤버 패널 드래그 시 떨림 수정
[Feat][DB] 위치 저장·조회 계층 구현
```

이슈 본문 양식:

```markdown
## 작업 목적
무엇을 해결하거나 구현하는지 작성합니다.

## 작업 내용
- [ ] 구현할 내용
- [ ] 검증할 내용

## 완료 조건
어떤 동작을 확인하면 완료인지 작성합니다.

## 참고 자료
관련 화면, API 명세, 이슈 링크를 작성합니다.
```

버그 이슈에는 `재현 방법`, `예상 결과`, `실제 결과`, `실행 환경`을 추가합니다.
스크린샷이나 로그를 첨부할 때 토큰·DB 접속 문자열·실제 사용자 위치는 제거합니다.

## PR 규칙

- 제목은 커밋과 같은 `<type>(<scope>): <변경 내용>` 형식으로 작성합니다.
- 작업 PR의 대상(base)은 **`dev`**입니다. `main`을 직접 대상으로 지정하지 않습니다.
- 하나의 작업 PR은 하나의 작업 목적을 가집니다. 여러 기능이 섞이면 PR을 나눕니다.
- 배포 PR은 **`dev` → `main`**으로 생성하며, 배포할 변경 목록과 통합 검증 결과를 정리합니다. 제목 예: `chore(release): v0.1.0 배포`.
- 본문에 변경 이유·주요 변경·검증 결과·연결 이슈를 작성합니다.
- 작업 PR에는 `Refs #12`로 이슈를 연결합니다. 배포 PR에는 완료된 이슈를 `Closes #12`로 정리합니다.
- UI 변경은 스크린샷 또는 짧은 영상을 첨부합니다.
- API 변경은 요청·응답 예시와 상태 코드를, DB 변경은 migration 및 기존 데이터 영향을 작성합니다.
- 테스트를 실행하지 못했다면 그 이유와 확인하지 못한 범위를 명시합니다.
- 리뷰어를 지정하고, 지적 사항을 반영한 뒤 다시 리뷰를 요청합니다.
- **작업 브랜치 → `dev`:** 승인 후 **Squash merge**하고 작업 브랜치를 삭제합니다. 병합 커밋 제목도 커밋 규칙을 따릅니다.
- **`dev` → `main`:** 승인 후 **Create a merge commit**으로 병합하여 두 브랜치의 공통 이력을 유지합니다. 배포 후에도 `dev`는 삭제하지 않습니다.

PR 본문 양식:

```markdown
## 병합 대상
작업 브랜치 → dev
배포 PR인 경우 dev → main으로 변경합니다.

## 연결 이슈
Refs #12
배포 PR인 경우 완료한 이슈를 Closes #12로 정리합니다.

## 변경 이유
이 변경이 필요한 이유를 작성합니다.

## 주요 변경
- 변경 내용

## 검증
- [ ] 관련 빌드 성공
- [ ] 변경 범위에 맞는 동작·테스트 확인
- 실행한 명령 또는 수동 확인 순서:

## 화면 / API / DB 변경
해당되는 경우 스크린샷, 요청·응답 예시, migration 영향을 작성합니다.

## 리뷰 참고
제약 사항이나 특히 확인이 필요한 부분을 작성합니다.
```

## 코드·데이터 관리 기준

- **iOS:** 같은 화면의 View와 ViewModel은 `Features/<화면>/`에 함께 둡니다. 모델은 `Models/<기능>/`에 둡니다.
- **서버:** HTTP 요청·응답 처리와 DB 접근 코드를 분리합니다. 사용자 입력은 SQL 문자열에 직접 붙이지 않고 파라미터로 전달합니다.
- **API:** JSON 필드·인증 방식·상태 코드 변경은 앱 담당자와 먼저 맞추고 서버 문서에도 반영합니다.
- **DB:** 이미 적용한 migration은 덮어쓰지 않습니다. 이후 변경은 새 migration 파일로 추가하고, 기존 데이터와 제약조건에 미치는 영향을 적습니다.
- **설정:** `.env`, 인증 토큰, DB 비밀번호, 개인 서명 파일은 커밋하지 않습니다. 공유 가능한 설정 형식은 `.env.example`에 작성합니다.
- **저장소:** iOS·서버·DB를 최상위 Git 저장소 하나에서 관리합니다. 하위 폴더에 별도의 `.git`을 만들지 않습니다.
